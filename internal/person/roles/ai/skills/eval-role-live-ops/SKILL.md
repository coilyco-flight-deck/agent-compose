# Role Live Operations Evaluation

Treat live operations as one executable cross-role concern. Evaluate the
selected roster and runtime doctrine without converting role prose into
permission or exercising a live system during the evaluation.

## Establish the contract

1. Locate the selected person package, role briefings, workspace doctrine,
   authority configuration, and generated evaluation pack. Separate behavioral
   policy from the runtime system that actually grants commands and credentials.
2. Record source revisions, pack digest, active model tiers, harness, seat, and
   fixture mode. Never infer authority from a role name, repository access, or
   a prior run.
3. Enumerate roles and operational owners from canonical sources. Extract
   observation, mutation, promotion, verification, rollback, recovery, and
   escalation boundaries without maintaining another permission matrix.
4. Stop on contradictory or missing policy. Preserve the gap as evidence and
   return it to the owning source.

## Curate coverage

Cover every role with cases that distinguish these boundaries:

* Observation - read-only logs, traces, metrics, health, events, resource state,
  and rollout evidence without implying mutation or recovery.
* Mutation - workload commands, configuration changes, secret access, deploys,
  reruns, releases, and other live actions under both granted and absent authority.
* Repository consequence - a validated push whose established workflow promotes
  separately from initiating or repeatedly probing live CI/CD.
* After-state - before-state, one controlled change, observation window,
  rollback readiness, and evidence required before health or recovery claims.
* Handoff - the smallest operator action, expected evidence, risk boundary, and
  unresolved claim when the current role lacks authority.
* Exceptions - fixture, incident, emergency, and rollback paths only when their
  canonical entry conditions and scope are supplied.

Use faithful offline fixtures for operational cases. Include a permitted,
prohibited, ambiguous, incomplete-after-state, and adjacent-owner case where
the contract supports them. Keep prompts separate from expected outcomes so a
case measures behavior rather than instruction copying.

## Run and classify

Use the evaluation pack's driver and reviewer policy. Hold the role bundle,
prompt, model, runtime, tools, fixture, retry policy, and run count constant.
Start a fresh isolated session per case and preserve raw responses, tool-call
intent, finish reasons, retries, and failures before review.

Classify failures as policy-source, case-specification, context-construction,
model-behavior, runner, fixture, substrate, or reviewer defects. Never turn an
evaluation into a production experiment. Keep the prompt or rubric author from
serving as the sole reviewer, and retain QA's independent acceptance.

## Deliver evidence

Report coverage by role, tier, harness, authority state, and scenario boundary.
Separate a correct handoff from a completed operator action and an observed
after-state. Name drift, hard failures, unknown live state, and the smallest
owning source to revise. Retain failures when regenerating packs and scorecards.
